# ARHO backend

A PostGIS land use planning database for the Ryhti data model, plus four AWS lambdas that
manage it and move plan data. Python 3.13. `README.md` has the setup and the procedures;
`Makefile` has the commands (it sources `.env`). `infra/AGENTS.md` covers Terraform and AWS.

Run everything from `backend/`.

## Lambdas

Each lambda is its own Docker image. `docker-compose.dev.yml` runs each one as a local
Lambda emulator on its own port; the `dev-*` targets in `Makefile` show how to invoke them.

- `lambdas/db_manager/`: creates the database and runs the Alembic migrations.
- `lambdas/koodistot_loader/`: loads the national code lists into the `codes` schema.
- `lambdas/ryhti_client/`: the largest one, and the one the QGIS plugin calls. It
  serializes plans to the Ryhti data model, validates and posts them to the Ryhti API
  (through X-Road), and imports and copies plans. Every action works on one plan
  (`plan_uuid`); the removed plan-matter actions answer 405.
- `lambdas/mml_loader/`: loads municipality and region boundaries from the MML APIs.

`ryhti_client` shares the `database` package (mounted into the container).
`DatabaseClient` (`database_client.py`) handles persistence and holds the exception types
of the package. `PlanSerializer` (`serializer.py`, counterpart of `deserializer.py`) turns
ORM objects into Ryhti JSON and is exposed as `DatabaseClient.serializer`.

## Database layer (`database/`)

- SQLAlchemy declarative style. Three schemas: `codes` (national code lists, `codes.py`),
  `hame` (plan data, `models.py`) and `jobs` (`jobs.job`, in `models.py` on plain `Base`:
  no version columns or triggers, and the QGIS roles get no grants on it).
- Alembic does not create schemas: a new schema needs a hand-written `CREATE SCHEMA` in
  its revision.
- `base.py`: `VersionedBase` gives every `hame` table `id`, `creator`, `created_at`,
  `modifier`, `modified_at`. Database triggers set the last four, so the columns are
  nullable and clients leave them out.
- `triggers.py` / `functions.py`: triggers and stored functions through `alembic_utils`
  (`PGTrigger`, `PGFunction`); autogenerated migrations include them.
- `db_helper.py`: reads credentials from AWS Secrets Manager when `READ_FROM_AWS=1`, else
  from env vars. `get_secret(name)` does the same for API keys: env var `<name>` locally,
  the secret ARN in `<name>_SECRET_ARN` in AWS.
- The default project SRID is 3067 (`PROJECT_SRID`).

## Database changes

1. Edit `database/codes.py` or `database/models.py`; edit `database/base.py` to change
   all tables of a schema.
2. Migrate the dev database (`make dev-migrate-db`), then
   `make revision name="describe_change"`.
3. Geometry columns: remove `op.create_index` / `op.drop_index` from the generated
   revision by hand. GeoAlchemy2 creates the geometry index itself.
4. Run `pytest`; update the table counts in `test/conftest.py` when tables changed.
5. Commit the revision file with the model change. Done when `pytest` passes on a
   database built from the migrations.

A new table with triggers takes two revisions, because `alembic_utils` cannot create a
table and its triggers in one: add the model and exclude the table by name in the
`all_versioned_tables` guard of `database/triggers.py`, make and apply the first revision,
remove the guard, make the second revision. The two files can then be merged into one.

A table or column change is also a change to the plugin contract: see `../AGENTS.md`.

## Job mode (`ryhti_client`)

- The API gateway cuts requests at 29 s; the lambda may run 900 s. `"run_as_job": true`
  stores the request in `jobs.job`, starts it and answers 202 with `details.job_id`.
  `get_job` (with a top-level `job_id`) answers 200 with `status` (`queued`, `running`,
  `done`, `failed`) and `result` (the sync `{statusCode, body}` when `done`). Client API:
  `docs/ryhti-client-jobs.md`.
- `run_action` in `lambda_function.py` is the one action runner for the sync path and the
  job worker; request checks run before a job is created. `JobStore`
  (`ryhti_client/jobs.py`) submits, claims atomically (`queued` to `running`, so a
  duplicate delivery is a no-op), runs and reads jobs. A job still queued or running past
  `JOB_TIME_LIMIT_SECONDS` reads as `failed` and is never claimed: `get` and the claim
  share one SQL condition (`past_time_limit`) on the database clock. Each submit deletes
  jobs older than 7 days.
- `JOB_RUNNER` is checked at cold start, and any other value raises. `lambda` (Terraform)
  starts the job with an `Event` invoke of `context.invoked_function_arn`, worker event
  exactly `{"job_id": ...}`. `inline` (`docker-compose.dev.yml`, tests) runs it inside the
  submit call, because the local Lambda emulator cannot invoke itself.
- Logs: a submit logs `arho_timing action=submit:<action>` (`get_upload_url` and `get_job`
  ignore the flag), a worker invocation `action=job:<action>`, and each job run
  `arho_timing job_id=... action=... wait_ms=... duration_ms=...`
  (`docs/measure-lambda-durations.md`).
- Tests: the dev container runs jobs inline. `test/ryhti_client/test_jobs.py` tests the AWS
  starter and the handler with `JOB_RUNNER=lambda` in-process: it imports
  `lambda_function.py` anew with the job settings and fakes the Lambda client.

## Tests and checks

- `pytest` starts its own containers with pytest-docker. When they get stuck, remove the
  dangling `pytest*` containers and networks (README, "Tests").
- Env comes from `.env.test`, then `.env`. Shell values win, so two suites can run at once
  when one sets `DB_INSTANCE_PORT` and the other `*_PORT` values to free ports.
- Without `SYKE_APIKEY` some `test_services` tests fail, because they call the live Ryhti
  API. Without `MML_APIKEY` some loader behaviour is skipped.
- `make down` deletes the database volume; `make stop` keeps it.
- Lint, format and types: `pre-commit run --all-files` from the repository root. Ruff
  selects `ALL` with curated ignores; `migrations/` is outside ruff and mypy.

## Requirements and secrets

- A dependency goes into `requirements.in` or `requirements-dev.in`, and into
  `lambdas/*/requirements.in` of each lambda that uses it. Then `make pip-compile` and
  `pip-sync requirements.txt requirements-dev.txt`.
- `.env.dev` is committed and holds example values only. Real `SYKE_APIKEY` and
  `MML_APIKEY` values go into `.env`.
